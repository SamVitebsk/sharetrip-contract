# ShareTrip Contract Service

## Назначение сервиса

Contract Service отвечает за договорные условия клиентов в ShareTrip.

## Текущее состояние

Реализованы с сохранением в собственной PostgreSQL:

- `POST /contracts` — создание черновика договора вместе с услугами;
- `POST /contracts/{contractId}/sign` — подписание существующего договора.

Остальные шесть операций (чтение договора, активный договор клиента, suspend, resume, terminate и проверка доступности услуги) пока возвращают `501`. Описание ответственности и взаимодействия ниже — целевая модель сервиса, а не перечень полностью готовых функций.

Слои разделены: `internal/api` преобразует HTTP-модели `gen` в Command/Result слоя `internal/service`; `internal/domain` проверяет бизнес-правила через Request/Response; `internal/repository` выполняет SQL и преобразует модели `entity`. Service задаёт порядок операций и границы транзакции, repository обеспечивает commit/rollback. Подключение и конфигурация БД находятся в `internal/postgres`.

## Ответственность сервиса

Contract Service принимает решения и хранит данные только в рамках договоров:

- создаёт договор для клиента;
- хранит статус договора;
- контролирует даты начала и окончания действия договора;
- хранит список услуг, доступных по договору;
- проверяет, доступна ли конкретная услуга клиенту;
- предоставляет внешний API другим сервисам;
- владеет собственной схемой хранения договоров и услуг.

Сервис принимает решение о доступности услуги на основании договора, его статуса, срока действия и настроек услуги.

## Что входит в границу сервиса

Contract Service владеет частью бизнес-процесса, связанной с договорными условиями клиента.

Внутри этой границы сервис отвечает за:

- создание и хранение договора клиента;
- определение текущего статуса договора;
- контроль периода действия договора;
- хранение набора услуг, указанных в договоре;
- хранение признака, разрешена или запрещена конкретная услуга;
- принятие решения о доступности услуги для клиента;
- предоставление API, через который другие сервисы получают это решение;
- собственную схему хранения договоров и договорных услуг.

Данные, которыми владеет сервис:

- `id` — идентификатор договора;
- `clientId` — идентификатор клиента;
- `status` — статус договора;
- `validFrom` — дата начала действия договора;
- `validUntil` — дата окончания действия договора;
- `serviceCode` — код услуги;
- `allowed` — признак доступности услуги по договору.

Услуги:

- `tripCreation` — право клиента создавать поездки;
- `tripParticipants` — право клиента добавлять участников поездки;
- `notifications` — право клиента использовать уведомления по договору.

## Что не входит в границу сервиса

Contract Service не должен:

- создавать поездки;
- изменять маршрут поездки;
- управлять участниками поездки;
- управлять жизненным циклом поездки;
- отправлять уведомления;
- выбирать канал доставки уведомления;
- хранить пользователей;
- выполнять аутентификацию;
- проверять роли пользователя;
- хранить юридические файлы договора;
- управлять оплатой, счетами и платежами.


## Взаимодействие с другими сервисами

ShareTrip Service обращается к Contract Service перед выполнением действий, которые зависят от договора клиента.

Пример сценария создания поездки:

1. Пользователь отправляет запрос на создание поездки в ShareTrip Service.
2. ShareTrip Service определяет `clientId` клиента, от имени которого действует пользователь.
3. ShareTrip Service вызывает Contract Service и проверяет доступность услуги `tripCreation`.
4. Contract Service проверяет активный договор клиента и условия услуги.
5. Contract Service возвращает `allowed = true` или `allowed = false` с причиной отказа.
6. Если услуга доступна, ShareTrip Service создаёт поездку.
7. Если услуга недоступна, ShareTrip Service возвращает ошибку пользователю.

ShareTrip Service использует внешний API Contract Service.

## Основные бизнес-правила

- У клиента может быть только один активный договор.
- Договор может иметь статус `draft`, `active`, `suspended` или `terminated`.
- Договор в статусе `draft` ещё не даёт доступ к услугам.
- Договор в статусе `active` может давать доступ к разрешённым услугам.
- Договор в статусе `suspended` временно не даёт доступ к услугам.
- Договор в статусе `terminated` завершён и больше не должен давать доступ к услугам.
- Договор действует начиная с даты `validFrom`.
- Если `validUntil` указан, договор действует только до этой даты.
- Услуга доступна только если она явно указана в договоре и имеет `allowed = true`.
- Отсутствие услуги в договоре означает отказ.

Планируемый алгоритм проверки доступности услуги (операция пока возвращает `501`):

1. Найти активный договор клиента.
2. Если активного договора нет, вернуть `allowed = false` и `reason = activeContractNotFound`.
3. Проверить, что договор уже начался: `validFrom` не находится в будущем.
4. Если договор ещё не начался, вернуть `allowed = false` и `reason = contractNotStarted`.
5. Проверить, что договор не истёк: `validUntil` не указан или находится в будущем.
6. Если договор истёк, вернуть `allowed = false` и `reason = contractExpired`.
7. Проверить статус договора.
8. Если договор находится в статусе `suspended`, вернуть `allowed = false` и `reason = contractSuspended`.
9. Если договор находится в статусе `terminated`, вернуть `allowed = false` и `reason = contractTerminated`.
10. Найти услугу по `serviceCode` в условиях договора.
11. Если услуга не найдена, вернуть `allowed = false` и `reason = serviceNotInContract`.
12. Если услуга найдена, но `allowed = false`, вернуть `allowed = false` и `reason = serviceDisabled`.
13. Если все проверки пройдены, вернуть `allowed = true`.

Ответ проверки должен содержать:

- `allowed` — доступна ли услуга;
- `reason` — причина отказа, если услуга недоступна;
- `contractId` — идентификатор договора, если решение принято на основании найденного договора.

## Локальная база данных

PostgreSQL запускается собственным `deploy/docker-compose.yml`; соседний проект не требуется. В Compose задан фиксированный проброс `6544:5432` на все интерфейсы хоста. Локальное подключение — `127.0.0.1:6544`; `PGPORT` в `.env` должен совпадать с портом хоста. Данные сохраняются в volume `sharetrip-contract_postgres_data`.

Скопируйте `.env.example` в `.env`. Для локального запуска в шаблоне задан пароль `admin`. Файл `.env` исключён из Git. Параметры `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE` используются для подключения; Compose создаёт базу и пользователя по этим настройкам при первом запуске пустого volume.

Из корня проекта выполните:

```sh
make up
make migrate-up
make migrate-status
```

`make up` ожидает готовности PostgreSQL. Для миграций Makefile устанавливает Goose фиксированной версии в `bin/`; нужен Go и доступ к зависимостям при первой установке. Пароль передаётся через окружение из `.env`, а не аргумент командной строки. Повторный `make migrate-up` не применяет уже выполненную миграцию заново.

Описание механизмов: [проверка готовности Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/), [переменные окружения Goose](https://pressly.github.io/goose/documentation/environment-variables/).

Изменение пароля или имени БД в `.env` не изменяет уже инициализированный volume. Используйте параметры существующей БД. Исходная миграция была исправлена с `company_id` на `client_id`; если у вас применена её старая версия, повторный `make migrate-up` не обновит схему. Не удаляйте volume с нужными данными: перенос старой схемы требует отдельного решения.

## Запуск и проверки

Нужны Go 1.25 или новее и Docker Compose. После подготовки `.env` и миграции выполните из корня проекта:

```sh
make run
```

Команда генерирует API-код, экспортирует `.env` и запускает приложение на порту `9190`. `.env` должен быть доверенным shell-совместимым файлом; его значения заменяют одноимённые переменные окружения. При прямом `go run ./cmd` или запуске бинарника файл автоматически не загружается — передайте `PG*` через окружение.

Config собирается в `cmd/main.go` через `env.String`/`env.Int`. При отсутствии настроек используются локальные defaults: `localhost`, порт `6544`, пользователь `postgres`, БД `sharetrip_contract`, `sslmode=disable`. Пароль берётся только из окружения. Неверный непустой `PGPORT` или порт вне диапазона 1–65535 завершает запуск с ошибкой. Для production явно задавайте параметры подключения и безопасный режим TLS; локальные defaults и публикация PostgreSQL на всех интерфейсах не являются production-конфигурацией.

При запуске проверяется соединение с БД. По SIGINT/SIGTERM HTTP-сервер останавливается, затем закрывается pool. Каталог `api/` должен находиться относительно рабочей директории, как в репозитории: он нужен Swagger.

```sh
make generate
go test ./...
go vet ./...
go build -o /tmp/sharetrip-contract ./cmd
```

Автоматических тестовых файлов пока нет: `go test ./...` подтверждает сборку пакетов. Результаты ручных HTTP/SQL-проверок, включая два конкурентных сценария и откаты, записаны в `HANDOFF.md`. Не запускайте проверку отказов на БД с нужными данными.

## Создание и подписание договора

Создание требует ненулевой `clientId`, `validFrom` и непустого списка известных услуг. `validUntil` можно опустить или передать null; иначе он должен быть строго позже начала. Период проверяется после усечения дат до микросекунд. Повтор кода услуги запрещён независимо от `allowed`.

```sh
curl -i -X POST http://localhost:9190/contracts \
  -H 'Content-Type: application/json' \
  --data '{"clientId":"11111111-1111-4111-8111-111111111111","validFrom":"2030-01-01T00:00:00Z","services":[{"serviceCode":"tripCreation","allowed":true},{"serviceCode":"notifications","allowed":false}]}'
```

Возьмите `contract.id` из ответа `201` и подставьте вместо `<contractId>`:

```sh
curl -i -X POST 'http://localhost:9190/contracts/<contractId>/sign'
```

Подписание возвращает `200` только для `draft`, который ещё не истёк (`validUntil > now` либо срок не задан). Будущее начало допустимо, но такой договор сразу становится единственным active клиента, даже если его период не пересекается с другим договором. Повторное подписание и переход из suspended/terminated запрещены. Истечение само по себе не меняет статус уже активного договора; автоматической смены статусов нет.

Обе операции возвращают полный договор в обёртке `contract` после commit. Подписание меняет только status/updatedAt. Услуги после чтения имеют стабильный порядок SQL-enum, не обязательно исходный порядок запроса. Смещение часового пояса в ответах может отличаться (`Z` или локальное смещение), момент времени сохраняется.

| HTTP | Код ошибки | Значение |
| --- | --- | --- |
| 400 | invalidRequest | Ошибка разбора, Content-Type, обязательного значения или кода услуги |
| 404 | notFound | Подписываемый договор не найден |
| 409 | conflict | Некорректный период, недопустимое подписание или конфликт уникальности. |
| 500 | internalError | Внутренняя ошибка без технических деталей в ответе |

Временное ограничение: по согласованному упрощению используется обычный `BodyParser`. Неизвестные JSON-поля игнорируются, отсутствие/null `allowed` становится false. Схема OpenAPI остаётся строгой — передавайте `allowed` явно и не полагайтесь на это послабление. Проверки бизнес-правил в domain при этом сохраняются.

## Спецификация API

Идентификатор стороны договора называется `clientId` в JSON и URL. Клиент — сторона договора; его идентификатор не равнозначен идентификатору пользователя.

Маршруты клиента:

- `GET /clients/{clientId}/active-contract` — активный договор клиента;
- `POST /clients/{clientId}/services/{serviceCode}/availability-check` — проверка доступности услуги.

Переход на эти имена несовместим с прежним API: старые маршруты не поддерживаются, запрос создания должен содержать `clientId`.

Точка входа — `api/contract.yaml`. Общие модели и параметры находятся в его разделе `components`.

Каждая из восьми ручек описана в отдельном файле в `api/paths/` и подключена через `$ref` в разделе `paths` корневой спецификации. Файлы названы по операциям в формате `snake_case`, например `create_contract.yaml` для `createContract`.

Файл ручки содержит HTTP-метод и описание операции. Ссылки на общие модели имеют вид `../contract.yaml#/components/schemas/ИмяМодели`, а на параметры — `../contract.yaml#/components/parameters/ИмяПараметра`.

Для добавления ручки создайте файл в `api/paths/`, подключите его в `api/contract.yaml` и выполните `make generate`. Общие модели и параметры добавляйте в `components` корневой спецификации.

Go-код генерируется командой `make generate` в `gen/openapi.gen.go`. Этот файл не следует редактировать вручную. В конфигурации генератора `import-mapping` связывает ссылки на корневую спецификацию с текущим пакетом, а `skip-prune` сохраняет компоненты, используемые из файлов ручек.

Для запуска выполните `make run` из корня проекта. Swagger UI доступен по адресу http://localhost:9190/docs. Сервис отдаёт корневую спецификацию по `/api/contract.yaml`, а файлы ручек — по `/api/paths/`. При запуске необходимо сохранять рядом с сервисом каталог `api` с этой структурой файлов.

После изменения корневой спецификации перезапустите сервис: Swagger middleware загружает её в память при старте. Если браузер показывает старую документацию, обновите страницу с отключённым кэшем.
